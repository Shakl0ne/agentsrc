# LLM 验证的「自动驾驶等级」

::: tip 论文信息
- **论文**：[《Grading the Graders: Verification Autonomy Levels (L0-L5) for LLM Reasoning》](https://arxiv.org/abs/2608.19009)
- **机构**：独立作者 Yajie Yin（该文为单作者预印本）
- **版本**：arXiv:2608.19009v1，2026 年 8 月预印本
- **阅读时长**：约 20 分钟
- **前置知识**：LLM 推理的验证机制（self-consistency、step verifier、形式证明）、「正确性 vs 完备性」基础、验证器的基本分类
:::

## 一、为什么「验证」也要被分级

LLM 越来越常用一个搭档：验证器。step checker、自洽性过滤、基于工具的事实核查、形式证明助手——它们都声称能抓出模型自己的错误。2023-2025 的文献里这类方案多到数不清，但几乎没人问过那个真正要先回答的问题：**一套验证方案，到底能保证什么，这份保证从哪来？**

关键在于「level（等级）」这个词在验证文献里被当成一个东西，其实代表的至少是五样不同的东西。论文直接列出这五条轴：

1. **Granularity（粒度）**——输出被拆多细来查：claim → sentence → document，或原子步 → 段落
2. **Concept abstraction（抽象层）**——验证运行在什么数学抽象的层级
3. **Risk / disposition（风险处置）**——结论触发什么响应：safe / unsafe / conditional 分级
4. **System stack（系统栈层）**——审计哪个组件：model → workflow → system
5. **Epistemic anchoring（认知锚定）**——结论所依赖的真实来源、以及它交付的保证强度

前四个回答「查什么、查多细、在哪一层、查完怎么办」，却没有一个回答决定验证器能否被信任的终极问题：**结论踩在什么 ground truth 上，它保证的是正确性、完备性，还是两者都不保证？**

论文主张第五根轴才是信任的关键，而且它有天然的六级结构（VAL L0-L5）。前三根轴经常被拿来冒充这根轴——正如第 2 章的不客气观察：**17 篇被调研的论文里，没有一篇把「锚」本身当成一个要建模的阶梯，也没有一篇把「验证方案自身的完备性」作为研究对象。**

这也和本站源码专栏互补：源码能讲清一个 skill、一个 harness 的验证步骤怎么写、挂在哪一层（granularity、system stack），而这篇论文回答「这个验证到底靠不靠得住、它到底能保证什么」——正是后面几根轴的领域。

## 二、论文怎么证明

要撑起「验证方案可以被一维分级」这个主张，论文用三块证据：**一套确定性的决策程序**、**跨四个领域的实证**、**一个文献梳理**。

首先，分类程序是确定性的。给任何验证方案，回答三个问题就定位等级：

- Q1（spec 来源）：验证条件（verdict 指向的东西）是谁声明的？(a) 被测 LLM 自己；(b) 从题目/代码里导出的确定性规则；(c) 独立于问题与生成机制之外的客观权威（金标答案、实测值、执行结果）；(d) 编码进可判定系统（symbolic solver、类型系统、阈值落地的决策规则）
- Q2（保证）：一个 PASS 承诺的是「每个提出的候选都满足条件」（正确性），还是「没有被漏掉的候选」（完备性）
- Q3（范围）：如果承诺完备性，它在哪个领域成立——单一属性、整类属性、还是声称的普适性

然后按一个「先命中就生效」的规则落到 L0-L5（Sec. 3.3，规则在 `val_standard.py` 里实现并带 11 个自测）。关键设计是程序刻意做成确定性的：**同一方案让不同人裁定必须得出同一等级**，唯一合法的分歧只在 Q1/Q2 的答案，而不在映射。

接着在四个领域各做一遍「同一协议」：先用标注数据建测试床，再测价值窗口（跟基线比），再分类失败模式，最后反过来测 judge 自己。四个领域分别是符号数学、行为监控、医疗诊断、代码生成（第四个方向上反着来：先写预测再找证据）。

## 三、核心发现

### 3.1 锚定源，是等级的唯一决定因素

每级由两个属性定义：**锚定源**（verdict 靠谁给）和**保证**（PASS 承诺什么）。由此推出三条性质：

- **决定等级的是锚，不是 judge**。一个校准得完美的 L2 验证器仍然是 L2：代入检查能证明某个候选满足方程，却没讲那没被提交的候选。把 L2 检查实现得更好（更密的采样、更好的阈值）只是 L2 内部横向移动；**只有换锚定源才能纵向升级**。
- **保证只能向下级降解，不能向上借**。为 L3 造的 judge（比如 symbolic solver）可以只当 L2 用（仅代入），程序会标成「可升级」；但为 L2 造的 judge，再怎么加数据也升不成 L3——**没有任何采样密度能补上完备性缺口**。这就是「更多数据不是升档操作」的来源。
- **每一级有它标志性的 abstention 行为，而且有诊断价值**。L0 系统否认错误（「自信地犯错」）；L1/L2 对自己没检查的部分保持沉默；L3/L4 对落在其 ODD 之外的属性返回确定性拒绝（论文点例：Safe 的「failed formalization」状态正是这个）；L5 不存在。

### 3.2 可靠性与等级正交，最严格的基线也承认相同的事

论文反复强调一个容易误导的点：**VAL 不是一个可靠度指标**。等级说锚的「认知状态」，不说 verdict 正确与否的概率；L2 验证器完全可能在 in-ODD 案例上比 L3 更准（论文自家 42/42 个单元测试就跨 L2 和 L3）。**等级与可靠度正交**，一个 L0 的 self-checker 也能在实际准确率上漂亮，只是没有确定性锚。

而文献里最严谨的形式验证基线——Lean 4 步级形式验证 [4]（论文里代号 Safe）——的作者自己写，验证器「关注每一步的正确性」：kernel 检查 LLM 生成语句的证明，但语句本身、以及它们编码的 case 覆盖，仍是 LLM 的声明。**盲区不会在梯子顶端消失，只是被推到「语句层」**。这是全文最有力的一处「对手方承认」。

### 3.3 完备性盲区：可以确认没什么漏掉，才是完备性

全文的中心论断（Sec. 4）用一句话钉死：

> 基于代入和采样的验证（L2）能证明「提出的候选都成立」，却不能证明「没有候选被漏掉」。完备性只能通过把属性重新编码进可判定系统（L3/L4）达成——或者根本做不到。

这个论断被论证为**定义性事实**（从代入和采样「是什么」推出），而非经验发现。给出四条支撑通道：

- **代入盲区**：代入检查只对已提交的候选求值，漏掉的候选「按构造不可见」——verifier 根本收不到它。数学实验里系统对一道真解为 {0,2} 的题提出 a=2，代入返回 PASS，漏掉的 a=0 检测不到。把它改写成解集相等（solveset 整式）后转成可机器判定的 FAIL，这正是 L2→L3 的本质：**是重新编码，不是加大投入**。
- **采样天花板**：采样验证在一组有限点上求值 P。它能否定（在采样里抓到反例），但不能定论（样本之间的空隙按构造察觉不到）。20 道题里三次「误 PASS」同因：漏掉的候选或内部空洞不在采样里。加密采样只是缩小天花板的影子，永远不会移走屋顶——这是 L2 范式的定义属性，不是调参变量。
- **语句层：盲区藏身处**。每套方案都在「被查的」和「被假设的」之间画一条线，**完备性盲区永远住在被假设的那一侧**。L2 的假设是「候选集是对的」；L3/L4 的假设上移但没消失：kernel 查证明，但定理陈述和它编码的分支覆盖是声明。
- **为何普适完备不可能（L5）**：不靠某个单一定理，而是「任意属性」这个说法打包了三类本就不可能普适的东西——程序语义属性（Rice 定理不可判定）、关于外界（自然界语言开放）的经验命题、无 ground truth 的主观属性。经验命题没法重编码成完备可判片段，最好的成果只能是锚定正确性（L2），或在形式化子片段上规则范围内完备（L3）。**proof checking 本身可判定**，这正是说明为什么完备性在受限可判定类（L3/L4）可达、在无限制类（L5）不可达。

### 3.4 四域实证：价值窗在「可报告性」，不在「准确率」

论文四个实证的「头条」是一串诚实的**负结果**（负结果是有意为之并写在定位段落里）：

| 领域 | 基线对照 | 结果 |
|---|---|---|
| 符号数学 | 依赖分解的 raw LLM 基线 20/20 三连 | 满架构反而 16/15/13——验证栈没提高准确率，偶有害 |
| 行为监控 | 统计偏离检测器（L2，阈值来自基线分布所以必然无完备） | 全局统计检测 holdout AUC 0.82, 真实输入下 FPR 崩到 92%；激励探测后 TPR 1.0/ FPR 30%；covert 攻击 4 个特性集 TPR 0.60 全程达不到 |
| 医疗诊断 | 教科书案例 10/10，硬例 8/10 | 两处失败同属「证据不足却自信结论」；信息完备性规则（L2）校准后 3/3 抓到过度自信，含人工复核漏的 #105 |
| 代码生成 | HumanEval 164/164（pass@1, temp 0.2, 非 greedy） | 去掉 type hint 也没留准确率余量 → 余量是空的 |

贯穿其中的恒定规律（Sec. 5.4）：**LLM 在训练分布附近的题上强到准确率窗口全空**（数学 20/20、医疗教科书 10/10、代码 164/164），不空的窗口全是「验证窗口」：数学的错误可报告性、行为的 ODD 约束检测、医疗的过度自信抓拍、代码的 L3 锚修复。一句话：**L2 的 judge 加的是可报告性，不是准确率；L3 的 judge 在自己的 ODD 内加的是完备性；任何东西都加不了 ODD 之外的完备性。**

## 四、对本站读者与工程实践的启发

这套分类最大的价值是当**部署前置检查单**，把自己对「我的验证到底多硬」有个诚实的刻度。落地到真实终端 / Agent 工程，论文给了一条工整的决策规则（Sec. 6.3）：**「属性可编码性 × 静默错误成本」决定要不要爬升**。

| 错误成本 \ 可编码性 | 可编码（有 ODD） | 不可编码 |
|---|---|---|
| 低错误成本 | 便宜就爬到 L3 | 停在 L1/L2，别过度投入 |
| 高错误成本 | L3/L4 必须 | L2 天花板 + 人工复核，标记风险 |

配合第 3.3 那条确定性决策程序 `val_standard.py`（带 11 个自测，样例：LLM 自检→L0；题目导出规则→L1；代入→L2；solveset→L3；Rust borrow checker→L4；普适完备验证器→L5 直接拒收），给三条实打实的工程建议：

### 4.1 别把「外部」当「独立」

VAL 的 L2 有个严格条件：**「客观」不意味着「在模型之外」而已，它必须对该模型所验证系统的错误机制独立。**另一个 LLM 给的答案在外部但不独立——它和被测系统共享同一个错误生成机制，这其实是「L0 假扮 L2」。执行系统、符号简化、物理测量才算数（它们的「错误机制」是工件本身）。部署时这是很实际的一刀：基于「另一个模型评」的结论，等级要按最弱的一环计。

### 4.2 可报告性 ≠ 准确率，买什么要分清

论文最大、可复制的负结果：**别人拿验证架构当「让准确率更高」，它给的是「让出错可见」。** 数学域满架构是负的，但 catch 到判别式错误、被抓改过答案 `[-1,1] vs 真实 [0,1]`、L3 solveset 抓到 L2 代入看不见的漏解。要推进准确率去买别的；要「在结果不可信的时候知道」才买验证。混淆这两根轴正是论文在 Sec. 2 花很大力气指出的类别错误。

### 4.3 升级靠重新编码，不靠喂更多采样

论文反复追这一条：L2→L3 的「找全部解」靠把任务重编码成解集等式、让属性变可判定，**没有采样密度做得到这件事**；L3→L4 靠一套可判定系统覆盖一整类属性。所以工程上「这验证不稳，多加样例吧」通常无效——先去问「属性能不能编码进可判系统、ODD 是什么」。

## 五、局限速写

论文第 7 节自己列的 8 条局限，最有分量的是这几条：

- **文献评估只到摘要级**：「17 篇里 11 篇 Abstract 级评估，6 篇主锚轴基于全文核对；其余可能随全文审查而变」——但它也把这一点做成了可审计：评估本身版本化（V1.0→V1.2→V1.3），并纠正过一条初始误判（L1/L2 改成了 L0/L1）
- **单模型 + 合成数据**：四域都用 deepseek-chat 单模型，医疗案例是虚构的、无真实患者数据
- **VAL 分类而不测量**：说了锚的认知状态，不给 verdict 正确概率；等级与可靠度正交
- **ODD 边界在现实里是模糊的**：「能否编码」依赖 solver/类型系统/规则输入，会随工具变化
- **VAL 自己也没被当测量验证**——没在规模上测过决策程序的 inter-rater 一致性
- **「错误可报告性」的价值被断言但没量化**：没报 judge 的真阳/假阳率、假警报成本，也没对这种准确率掉 25–35% 的净代价；假警报多于真捕获时，净收益为负——这一点论文自己也承认待证

## 六、深度理解问答

### Q1 为什么「爬高验证层」不等于「更可靠」

因为 VAL 分的是**锚定来源与保证**，不是正确概率。论文明确「VAL 不是可靠度指标」：一个 L2 的验证器可以比一个 L3 的验证器在 in-ODD 案例上更准（论文自家的 42/42 测试就跨 L2/L3）。层级管的是「这张 verdict 能不能被信任到哪一级、保证到哪一层」，实际正确率另是一根轴。实现上的采样更密、阈值更好，都只是在同一层内移动；只有换锚才能纵向走。

### Q2 那最推的最先进验证（Lean 4 步级证明）算什么

按 VAL 它是 **L4 kernel + L0 语句层**：kernel 对一个给定 statement 的证明做形式化检查（这可判定，见 §4.5），所以层级能达到 L4；但 statement 本身、及它编码的分支覆盖，仍是 LLM 生成且未经验证的声明，即 L0。所以一个「定理已证」的 claim 是 L4，一个「答案正确」的 claim 是 L0——系统级不是单一标量，**分 claim、分部件地组合**。这也解释了前面那句「盲区被推到语句层」。

### Q3 那「验证到底应不应该用」在有判定权衡时怎么选

不是「越高越好」。论文关键一句：同一份 verdict 文案（「有效」）在不同层级下的份量天差地别，框架存在的意义就是让这份差别可见。 规则回到第 4 段表格：低错误成本且不可编码，停在 L1/L2 不花冤枉钱；高错误成本且可编码，L3/L4 是硬要求；高错误成本又不可编码，诚实停在锚定正确性 L2 兜底 + 人工复核，把风险明说。一个低 stakes 摘要器的 L0 自查是正当的，用于出院摘要生成就是极其危险的事——正确与否不取决于文案，取决于哪个层级在说这句话。

### Q4 那「完备性」永远够不着怎么办

不用绝望，但也不必假装能全局拿到。完备性是**有局部的可用**（在 ODD 内、L3/L4）、**无全局的可用**（L5）；工程问题永远是「选哪个 ODD、跑到哪一层、怎么拒绝」，而不是「追不追完备性」。论文给出的落地抓手很实在：把问题重编码成可判定判断（如用 solveset 求整式解集），就能把「L0 的 LLM 自评」换成一个边界干净的 L3 判定器，代价小、判定栈清晰；整套机制可以平移到一个 agent harness 里，去验证它自己的断言输出。

## 七、结论

一句打包，再拆三句：**验证的等级由「谁给了要被验的规格、这个 verdict 保证什么」这一根轴决定**——不是查得细、查得深、查得层数多就等于更硬；**完备性盲区是范式属性，不是调参问题**——代入和采样能证明无误判的候选，却永远证明不了「没有漏」，它不是换更多数据能补的；**工程上赢的不是「最硬的验证」，而是「知道自己多硬并明说」**——L2/L1/L0 在低错误成本场景是正当答案，在高错误成本场景则以诚实标注边界、把锚定递归终止在可判定内核上。
