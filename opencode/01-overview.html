OpenCode 整体架构：一个 10 万行 Agent 怎么被组织成一条装配链 ​

如果让你来设计一个能在终端运行的 AI 编程助手——源码拆分为数十个包、上万个文件，需接入 30 多家模型厂商，且要在同一个进程中同时管理命令行、HTTP 接口、WebSocket、插件与快照……

如此庞杂的系统让你来设计，如何保持架构清晰？

常规思路往往是从 runLoop 开始，让模型先跑起来。但在几万行的代码规模下，真正让系统保持稳定的并非某一个主循环，而是将其组织成一条「装配链」：入口、运行时、模型、持久化、扩展各守其位，最终拼装成一个整体。

本文的任务，就是先搭起这张总地图。

看完这篇，你将理清三个核心问题：

  • 第一，这个 10 万行引擎被拆成了哪几块，为什么是「契约 / 模型 / 实现」三体；
  • 第二，一个命令从你按下开始，是怎么一步步装配并运行起来的；
  • 第三，持久化和扩展是怎么长出来、却不把主干拖乱的。

这一篇先从「设计一个通用 Agent 引擎到底面临哪些核心挑战」说起。主循环、工具和上下文这些细部机制，放到后面的文章再往下拆。

一、先把问题摆出来：做一个「通用 Agent 引擎」的摊子有多大 ​

1.1 一个能想象的任务 ​

想象你被要求做一个通用的、开源可扩展的终端编程 Agent。不是给自家某个模型写个玩具，而是要让它：

  • 能接几十家不同厂商的模型——Anthropic、OpenAI、Google、以及一堆开源可兼容的协议端点；
  • 既能当 CLI 命令行跑，又能被 Web / SDK 拉起来当服务；
  • 还得让人写插件扩展它的行为，而不需要改它核心。

在你动手敲第一行 run() 之前，先把这件事摊开看：它不是一个「循环」，而是四类完全不同的负担叠在一起——模型差异、运行时主循环、持久化、可扩展性。

1.2 先拆出四类负担 ​

把「通用 Agent 引擎」的复杂度摊到桌面上，其实是四堆互不相干的问题：

负担它的本质要回答的问题
模型差异各家厂商的接口、协议、能力都不一样怎么用一个抽象把几十家 说得不同 的模型统一进来
运行时主循环模型不是一次性，是要「感知→分析→行动→反馈」反复迭代这个迭代的骨架如何维持稳定，而不至于散落一地
持久化Agent 是一次又一次的会话，中途崩了要能续上状态存哪、怎么查、怎么升级
可扩展第三方要能用、能改怎么让别人叠加能力而不改内核

这四个问题，正是后面所有章节要解决的四个「为什么」。而 OpenCode 给的答案有一个共同的形式：把每一种负担，都变成一个独立的、可替换的「层次」，再用一条装配链把它们拼起来。 先把引擎本身分成哪几块讲清楚。

二、三大引擎包：为什么是「契约 / 模型 / 实现」三体 ​

先看 OpenCode 真正的代码骨架。它不是一个包打天下的巨石架构（Monolith），而是一个有边界、有依赖方向的 monorepo——核心引擎由三个包构成：core、llm、opencode。

2.1 core：契约 + 厂商接入基座，是整个系统的底座 ​

packages/core 是整个系统最底的一层基座。它放的东西有两类：

  • 类型与契约：session、message、agent、model、tool-output、provider……这些是系统的「名词表」，规定“一个会话长什么样”“一个模型长什么样”。
  • 厂商接入基座：它的 src/plugin/provider/ 下放了 30+ 个 Provider 适配器（Anthropic、OpenAI、Google 等）。厂商接入并非硬编码，而是插件式的。新增厂商只需实现一个 adapter 挂载到 provider/ 目录下，这也是系统能兼容 30 多家模型而不乱的根本原因。

2.2 llm：独立的模型协议层，把「厂商协议」抽象成可换的一块 ​

模型相关的逻辑其实分为两层：一层是上述的「每个厂商怎么接」（core 的 adapter），另一层是「怎么按协议对齐」。OpenCode 把它单独抽成 packages/llm。

llm 包是个独立的模型协议层——它把各家厂商的报文、认证、路由整理到底层的公共 abstraction（Protocol / Endpoint / Auth / Framing 四个维度），依赖面很轻、基本只与基础件（如 effect）耦合，不和 session、运行时缠绕。这意味着，「模型接入」在整个引擎中是完全解耦、可独立演进的一环。这不是实现细节，而是设计上的一个刻意分层决策：模型层的稳定性，不该被运行时里那些频繁变动的逻辑一起裹挟。

2.3 opencode：所有「运行时实现」的家 ​

packages/opencode 是三个包里最大的一块，也是真正干活的引擎：session/（会话与主循环）、tool/（几十个内置工具）、server/（HTTP 服务）、mcp/、skill/、snapshot/、storage/（SQLite 持久化）、git/、permission/……几乎除了「契约」和「纯模型协议」之外，一切实现都在这里。

2.4 三者如何协作：依赖方向决定了谁在底座 ​

把三块放一起，依赖方向非常清晰：

  • core 在最底，什么都不依赖（不依赖任何内部包，只靠纯 npm 外部件）；
  • llm 独立中立，也和内部无强耦合；
  • opencode 在最顶，同时依赖 core、llm、sdk、plugin、ui、script 等内部包——它是「装配链」上把别的包拼装成完整可运行系统的那一段。

从代码量来看（仅统计 src 下 TypeScript）：core 约 1.2 万行、llm 约 8700 行、opencode 约 8.7 万行——三包合计约 10 万行量级，其中实现层占了绝大部分。

顺着这条装配链，我们先把「层怎么分、链怎么接」看清楚。

三、一条装配链：从你敲命令到它跑起来 ​

这三个模块拆分好后，还只是静态的代码包；真正让系统活起来的，是它们被装配成一条链。这条链的入口只有一个。

3.1 单一入口：一个 index.ts 拉起整个运行时 ​

packages/opencode/src/index.ts 是唯一入口，用 yargs 装好 20+ 个子命令（run / serve / tui / acp / mcp / providers / agent / …）。真正常驻的是 serve：它拉起一个 Engine runtime（Effect 装配的运行时），同一个进程里同时提供 HTTP API 和 WebSocket 两类接口。

这里的 Effect 是这套引擎的依赖与执行编排库：把各服务的创建、注入、异步与对外操作组合成一张可执行的蓝图，再由同一个 runtime 统一跑起来。它不只在 3.1 出现——后面章节里的 Effect.fn、Effect.Schema、forkIn 都从这一个心智模型长出来。

  • 这也意味着：终端里敲 opencode(CLI) 和网页里连它 (Web/HTTP) 是同一套引擎，只是暴露了不同的入口——设计上省去了一大笔「重复实现」的成本。

3.2 会话主循环：一条可以反复执行的路径 ​

引擎起来之后，核心是 session 里的主循环（session/processor.ts）：它承接一个 prompt，进入「感知 → 分析 → 行动 → 反馈」的迭代，直到模型决定停下来/输出。工具的执行、压缩的触发（上下文溢出）都在这个循环里被安排。

这一篇先停在这张总图上。你先抓住一点：它是那条「装配链」的中心骨，所有其它层（模型、工具、持久化、插件）都挂在它身上来回打转。 具体到每一格怎么走、事件怎么处理，放到后面的文章再拆。

3.3 一条链的结果：各守一段，化整为零 ​

从上到下将整条链路梳理一遍： 入口（index.ts/serve）→ 运行时 → 会话主循环（processor）→ 模型（core adapter + llm）→ 工具执行 → SQLite 持久化 / plugin-mcp-skill 扩展。

每一步都清楚自己「从谁手里接、往谁手里送」。换句话说，节点各守一段，接口清楚，单点替换也不至于把整套系统一起带歪。

四、持久化与扩展：状态怎么落地，能力怎么外挂 ​

装好了主链之后，还有两块把「系统从能跑到可用」补齐：持久化保证了状态的可恢复性，扩展性则赋予了系统生长的空间。

4.1 持久化：状态可查，还能安全升级 ​

Agent 是反复的会话，状态不能都压在内存。OpenCode 用 SQLite + Drizzle 做持久化（schema 在 session.sql.ts / storage 里定义）。其核心抽象在于：将状态落盘为「具备可查询结构的数据库」，而非仅仅以纯文本形式进行追加（append-only）——从而保证程序可审计、可恢复。

4.2 扩展面：拓展行为而不动核心 ​

它让第三方能扩展，靠的是 plugin（公共包，供外部插件作者用）+ mcp + skill + snapshot + background 这些挂在运行时之上的能力。关键是：你要叠加一个新能力，不需要碰核心引擎——插件做成一个「机制」外挂在运行时，还受 permission 约束。这和后面聊 plan-execute-verify 时「插件在原生 hook 上叠加策略」的思路是一脉相承的。

五、这套分层最后留下了什么 ​

5.1 五条好用的抽象 ​

回头看整篇，这套体系更值得带走的，是五条抽象，而不是某段代码：

  1. 契约底座先行：core 只放类型与厂商接入基座，不依赖任何内部包——「名词」和「动词」分干净。
  2. 模型层独立：llm 把厂商协议独立成包，模型接入是可评测、可换的。
  3. 单一入口：CLI 和 Web 用同一引擎，一个 index.ts 装配起所有子命令。
  4. 一条装配链：入口 → 运行时 → 会话主循环 → 工具 → 持久化 / 扩展，层层咬合。
  5. 扩展不拆：插件 / mcp / skill 栓在运行时外围，受 permission 门控，不动内核。

5.2 设计哲学：复杂度先切层，再谈规模 ​

总结来看，OpenCode 的设计哲学可以概括为一句话：一个系统能做大而不乱，靠的不是某一行代码，而是有没有一开始就把复杂度切成有边界的层次，以及每层是否只守一件事。

它把全栈用 Effect 一统（贯穿 core 的 Schema、opencode 的运行时装配、HTTP 服务），依赖注入和声明式装配也因此能一路贯通。模块一多，这种写法反而更稳：引擎是「装配出来的」，不是「内联写死」的。

5.3 Effect：把"要做什么"与"怎么做"拆开，再统一编排 ​

前面说的"装配出来"落到机制上，靠的就是 Effect。它是一个"声明 + 执行分层"的编排库。

  • 声明与执行分离：你写的是一份"要做什么"的蓝图——各服务怎么创建、按什么依赖顺序组装、出错怎么兜底。真正"动手去做"（读写文件、调接口、发请求）由一个 runtime 统一完成。写代码的人描述的是依赖关系，而不是亲手碰执行的细节。
  • yield* 的读法：它不是在等一个协程，而是"把这一步蓝图拼到外层蓝图里"。每一小步都可暂停、可中断、可失败，由引擎统一处理，而不是散落在业务代码里各写一套 try/catch。
  • 依赖注入：Service 只定义到上下文（Context）里，测试和生产可以注入不同实现。这正回答了 2.4 的"谁依赖谁"和 3.2 的主循环为什么能只认接口不看实现——同一份逻辑，换一层注入，行为就变。
  • 一句话类比：可以把它当成"在 Promise 之上，多了一层『可组合、可换实现、可随时喊停』的编排层"。后面涉及的 Effect.fn、Effect.Schema、forkIn 等概念（主循环、工具、压缩三章都会用到），均源于这套心智模型。
