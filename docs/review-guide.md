# 文章校验指南

> 本站（agentsrc）**写后校验**规范。适用于所有专栏（Claude Code / OpenCode / Codex / 新增专栏）的已写文章。
> 生效时机：**文章写完、交付前**，由另一个 agent 独立执行。校验的目标是确保文章在两层上都站得住：**事实正确（源码对齐）** 与 **论述自洽（+ 抽象完整）**。两轮缺一不可。

---

## 一、校验的角色定位

- 校验是**独立于写作的一条流程**：写作时的规范（选题/结构/手法）不在本文档范围，本文档只管"成品对不对、严不严、好不好读"。
- 校验者应带着审读而非写作的视角：**查证时不带"怎么写更好"的负担，通读时不带"对齐源码"的负担**，每轮只用一种认知模式，避免来回切换损耗。
- 校验者负责**发现问题并标记**；是否改动、怎么改，由文章负责人决定。

---

## 二、第一层：源码对齐（事实正确）

机械校验声明，人工判断断言。脚本只能告诉你"这个名词在源码里是否存在"，判断"说得对不对"仍需人工走读源码。

### 校验清单

1. **文件/路径存在**：正文引用的文件名/路径确实存在于官方仓库？
2. **关键定义匹配**：提到的接口名、函数名、数据结构在源码中能找到对应定义？
3. **流程顺序贴合**：画的流程图/顺序图与源码实际执行路径完全一致？
4. **版本准确**：引用的源码版本与文章标注一致？是否混入了更晚版本的说法？
5. **对比有据**：跨系统/框架的对比有源码机制支撑，而非主观感受？

### 机械校验示例

源码镜像已 clone 到 `career/agent/` 目录，验算时直接引用：

```bash
# 例：确证某符号存在于 OpenCode
grep -ri "runLoop" agent/opencode/src/
# 例：确证某方法存在于 Claude Code
grep -ri "StreamingToolExecutor" agent/claude-code-main/src/
```

> 注意：`grep` 只能证明"存在"；上下文逻辑与结论是否正确仍须人工走读源码（或在源码镜像里直接 read 目标文件）。

---

## 三、第二层：论述自洽 + 抽象完整

在事实无误后，通读全文做 4 个维度检查：

1. **层次划分合理**：文章分层/模块划分有源码边界吗？分法统一（如按功能域、按持久性）；分法是否都有源码依据，层与层抽象级别是否一致，有没有把不同抽象层级混在同一层？
2. **前后一致、无矛盾**：同一概念在不同位置说法一致？早期引用的数字/公式/逻辑在后文用到时仍成立？文章基于某版本分析，中间是否混进更好版本的描述而未标注？
3. **覆盖无遗漏 + 抽象完整**：每个层级/模块是不是"是什么 + 为什么 + 怎么做到的"都讲清了？每个设计取舍是否讲清了**选择原因**（为什么选它而不选别的）？讲的是一个完整流程，还是只讲了一种触发路径而漏了另一条？
4. **可读性检查**：长段代码能否用 2-3 行总结替代？流程图能否精简而不损失信息？有没有"读者看到这里会困惑"的非线性跳跃？

### 抽象优先的审读原则

本站文章以**抽象流程与设计思路**为纲。因此审读时对每个细节追问：

> **这段是"支撑论证"，还是"被无关实现的拖累"？若删掉后主线仍通，就应删。**

- 抽象完整 ≠ 罗列代码：细节只作为论证抽象的证据，随文出现、点到即止。
- **抽象优先意味着每个细节都必须能证明自己存在的价值**；无法服务于设计论证的实现细节属于噪音。

---

## 四、审校流程建议

为减少逐段切换上下文的损耗，建议**按角色分批**完成：

1. **源码对齐轮**（针对性查证）：只查源码，不看文章写法。带着正文出具事实声明（文件名、函数名、常量值、流程步骤），逐条在源码 grep/read 确认，标记差异，把差异记入问题清单。
2. **结构审校轮**（通读检查）：确认事实无误后，从头到尾通读全文。不带源码，只关注论述自洽与抽象完整（层次、一致、覆盖、可读），把发现记入问题清单。
3. **最终一致性检查**：扫一遍全文，确认早前的标记没有引入新的前后矛盾（编号、引用、关键词）。

两轮分离的好处：查证时不需要"写文章"的视角，通读时不需要"对齐源码"的负担。**校验者全程只做审计与标记；实际修改由文章负责人执行。**

---

## 五、修复原则

- 源码已更新导致文章过时：在文章中标注版本号和时间点，注明"截至 X 版本"。
- 不硬套最新版本：文章核心价值是讲特定版本的实现思路，而非追最新 commit。
- 差距过大：append 一段"版本更新说明"，而不是全文重写。

---

## 六、校验产出交付

校验结束应交付一份**问题清单**，按两层区分并给出证据：

| 层 | 问题示例 | 依据 |
|----|---------|------|
| 源码对齐 | "引用了不存在的 request.ts" | 仓库中无此文件 |
| 源码对齐 | "Reference 的 @refname 语法未实现" | grep 无匹配 + 走读确认 |
| 结构审校 | "2 轮对话未说清是消息条数还是完整轮次" | 前文定义不一致 |
| 结构审校 | "compaction 隔轮机制只讲了结果未讲原因" | 抽象欠缺 |

将清单按"源码对齐轮 / 结构审校轮"分类提交，便于负责人按层修复。
