# 写作指南

> 本站（agentsrc）通用写作规范，适用于所有专栏（Claude Code / OpenCode / Codex / 新增专栏）。
> 本文档是**写作的唯一权威**：选题、结构、写作手法、抽象层次、署名、小测全部以本为准。概念图生成与构建/部署由站级工程文档负责。

---

## 一、核心写作原则（先读）

写作前先记住这条主线，它决定整篇文章的取舍：

> **写"抽象流程与设计思路"，不抠无关紧要的实现细节。**

- 文章的主线是**系统的抽象层次**：它把问题拆成哪几层、每层负责什么、层与层怎么协作、设计者为什么这么分层。读者要带走的是"**为什么这么设计**"，不是"这行代码什么含义"。
- **细节是支撑，不是主角**：代码/常量/行号等具体实现只作为论证流程与思路的证据**随文出现、点到即止**，绝不铺陈。一段 15 行能被 2-3 行总结替代的代码，就该被总结替代。
- **判断标准**：删掉这段，读者还能不能跟上设计主线？能，就删或压缩；不能，才保留。**只剩具体实现而无助于理解设计意图的细节，属于噪音。**
- 全文要让读者看完能回答"这个系统是怎么被设计出来的、为什么这么设计"，而不是"这个函数第几行返回值是什么"。

### 与图片/源码的关系

- 图片、流程图、源码片段都是**辅助叙述设计的工具**，不是目标本身。它们服务于"讲清抽象"，不反客为主。
- 具体实现（函数名、行号、枚举值）作为**证据**出现在正文，但**不构成正文的主线**。

## 二、整体写作风格

| 维度 | 定位 |
|------|------|
| 语气 | 亲和、平实，像是经验丰富的同事在分享 |
| 难度 | 中等偏深，默认读者有一定基础但不预设专家 |
| 节奏 | 简洁明快，每个段落控制在 2-5 句 |
| 人称 | "你"（读者）+ "我们"（共同探索），**正文不出现作者自称** |
| 叙述 | 中性技术叙述，作者身份与正文区隔开 |

### 作者署名与身份

| 用途 | 名称 |
|------|------|
| 文章署名/作者展示 | `shaco`（全小写，无空格） |
| GitHub 用户名 | `Shakl0ne` |
| 导航 GitHub 图标链接 | `https://github.com/Shakl0ne` |

禁止出现：
- ❌ "凌皓"、"小林" 等其他化名
- ❌ 大写 "Shaco" 或驼峰 "ShAco" 等变体
- ❌ 在文章正文里自称（如 "我" 作为作者），正文保持中性叙述口吻

发布前一致性检查（期望输出为空）：

```bash
grep -rn "凌皓\|小林" --include="*.md" .
```

### 语言特征

1. **善用设问作标题和段落引导**："为什么用 X 而不用 Y？""这个机制是怎么实现的？"
2. **具体数字增强可信度**："51 万行泄漏代码"、"200 个 package"、"86,715 行 TypeScript"
3. **"源码精读"作为品牌标签**：本站定位是"告诉读者为什么这么实现"，不是"怎么用"
4. **对比结构清晰**：有对比的文章形成鲜明结论（如 "dsh vs 终端编程 Agent 的同能不同构"）
5. **抽象优先贯穿始终**：始终围绕分层、边界、协作、设计取舍展开

## 三、选题与标题

### 选题类型

| 类型 | 标题模式 | 示例 |
|------|---------|------|
| 教程类 | `XX 指南：怎么 XX？` | CLAUDE.md 指南：项目记忆该怎么写？ |
| 深度解析类 | `XX 图解：核心机制怎么做？` | 多 Agent 图解：SubAgent 机制怎么做？ |
| 源码拆解类 | `XX 源码拆解：N 行代码里的架构设计` | 51 万行代码里的架构设计 |
| 对比评测类 | `A vs B：同一需求实测，差距在哪？` | 2 种上下文压缩机制对比，哪个更好？ |
| 案例研究类 | `N 万次会话研究：XXX` | Anthropic 40 万次会话研究 |

### 标题公式

```
[关键词/动作] + [冒号] + [疑问/承诺/场景]
```

### 选题原则

- **抽象优先**：选题选"某个设计思路/架构取舍"，而不是"某个函数细节"
- **拆解复杂概念**：把黑盒概念打开（"为什么用 X 方案而不用 RAG"）
- **解决真实问题**：来源使用/面试中的痛点
- **提供对比视角**：同类机制对比，帮读者建立判断
- **源码根基**：每个观点需源码/配置/数据支撑

## 四、两类文章结构

本站文章主要分两类：**源码解析类**（长，深）与**教程类**（中，浅）。

### 源码解析类（10K~13K 字）

```
H2: 一、[章节标题]（背景铺垫/设计取舍）
  [问题场景] + [类比]

H2: 二、[章节标题]（核心抽象A —— 层/模块/职责）
  H3: [子抽象A1]
    [设计意图 → 支撑源码（短）→ 讲解设计思路]
  H3: [子抽象A2]

H2: 三、[章节标题]（核心抽象B —— 协作/流程）
  H3: [子抽象B1]、[B2]

H2: 四、[章节标题]（隐藏特性 / 边界条件）
   [假设 → 追问（触发什么流程）→ 答案]

H2: 五、[章节标题]（横向对比 / 设计启示）
   [对比表]
   [设计哲学总结]

H2: 六、[章节标题]（总结，N 条核心设计原则）
```

- **层级**：3 层（H1→H2→H3），每节 2~5 个小节；编号 `一、二、三、…`
- **主线是抽象**：每一节 H2 代表一个抽象层次（层/模块/流程），H3 是该层下的关键设计点。源码只作为该点的论证证据，短而精。
- 由浅入深推进，最终落在"设计哲学/工程启示"。

### 教程类（5K~7K 字）

```
H2: 01｜[核心概念]
H2: 02｜[常见误区]
H2: 03｜[有效方法]
H2: 04｜[进阶理解]
H2: 05｜[实操步骤]
H2: 06｜[参考模板]
H2: 收尾：N 句话精华
```

- 层级：2 层（H1→H2），编号 `01｜02｜03….`
- 以"实操"为目标，可常用"不要…要…"对比、"X≠Y"辨异

### 两类型对比

| 维度 | 源码解析类 | 教程类 |
|------|-----------|-------|
| 字数 | ~10K~13K | ~5K~7K |
| 标题层级 | H2×6, H3×20+ | H2×7~8 |
| 编号风格 | 一、二、三 | 01｜02｜03 |
| 代码块 | 8~10 处 + 行号 | 1~2 处 |
| 表格 | 2~3 个对比表 | 1~2 个 |
| 配图密度 | 每节末 1 张 | 约 5~6 张 |
| 读者定位 | 有源码阅读能力 | 所有目标用户 |
| 主线 | **抽象/设计** | 操作/上手 |

## 五、段落写作模式

抽象原则下最常用的模式是"**问题 → 设计思路**"（模式 4、5、6），把细节折叠进论证。

#### 模式 1 — 场景设问
```
想象你让一个 agent 去做这么一件事：「[任务]」。
这一套下来有 [N] 个问题：第一，…；第二，…。
```
（先把读者放在要解决的问题前，为"设计思路"铺路）

#### 模式 2 — 问题 → 答案（"先别往下翻看答案"）
```
先抛个问题：如果 [条件]，会怎样？先别往下翻看答案。
公布答案：[答案与设计意图]。
```

#### 模式 3 — 类比说明
```
[概念] 说白了就像 [类比对象]：类比只负责 [职责]，主角负责 [职责]。
```

#### 模式 4 — 假设 + 追问（抽象推演，核心）
```
既然 [设计如此]，那冒出个问题：[某个流程/边界怎么走]？
系统用一个补丁 [机制] 解决。
```
**用法**：用来带出"为什么会这样设计"，是本文照常的核心推进手法。

#### 模式 5 — 源码展示 + 翻译（支撑，不承载）
```
对应到源码，是一个叫 [函数] 的函数：
[// 源码位置：path/to/file.ts:line]
[源码片段 5-20 行]
你看这几行，对应的是上面讲的 [N] 个设计点：[设计意图]。
```
**约束**：代码**必短**（5-20 行），**必须前后有讲解**，作用是**论证一个抽象点**，不是逐行说明书。

#### 模式 6 — 总结提炼 + 设计启示
```
[机制] 单独的细节，但对设计的启示是：很多人只关心能不能跑起来，不关心 [可维护/成本/可靠性]。
所以 [核心设计辞] 本身就是能力的一部分。
```

#### 教程类特有模式
- **模式 7 — "不要…要…"**：正反对照
- **模式 8 — "X≠Y"辨异**：澄清误解
- **模式 9 — 反例 → 正解**：先错后对

### 互动性设计
- "先别往下翻看答案"、"凭直觉你可能觉得…但答案是"、"我建议你先停 10 秒想想"、"猜一下"

## 六、内容呈现规范

### Markdown 使用

| 元素 | 规范 |
|------|------|
| 标题 | `#` 仅用于文章标题，其余 `##`/`###` |
| 列表 | 无序 `-`；有序 `第一、第二…` 或 `1.` |
| 代码 | 行内反引号；代码块三个反引号 + 语言标注 |
| 加粗 | 强调关键概念或文件名 |
| 引注 | `>` |
| 分割线 | 每页**至多一条** `---`（不含 frontmatter 首对），正文 0 或 1 条 |

### 代码块规范
- 源码展示 **5~20 行**，不要过长
- 标注源码位置 `// path/file.ts:line`
- 前后都配讲解；源码尽量浓缩为"抽象论证的一个证据"

### 配图规范
- **什么时候配图由写作决定**：配图是为辅助理解抽象流程与设计思路而生，每篇至少 1 张核心架构/流程图，源码解析类每节末 1 张
- **一张图传达一个设计点**：明确"这张图帮读者搞懂什么设计取舍"，再生成，避免装饰性配图
- **图片只辅助抽象定位**，具体描述留在文章正文
- 视觉风格（深色未来主义、配色、构图、场景模板）、命名、存放到站的**配图生产规范**；写作时只需按约定命名并存放

## 八、章节小测（Quiz）

每篇末尾带一节 `<Quiz>` 小测，规则（避免"答案从题干一眼看出"）：

1. 四个选项**等长**：正确项不得明显比其他长/具体，最长的正确项属于不合格
2. 加大难度，干扰项要"看似合理"：做"概念混淆""边界细节说反""机制张冠李戴"，而非明显凑数
3. 每个选项半角引号 `'…'` 包裹；`correct` 从 0 计且与正确项一致；`explanation` 解释"为什么对 + 为什么其他错"

> 自测题（尤其源码解析类）也要考"抽象与设计思路"，而非死记某一行代码。

## 九、避坑要点

1. 不要假设读者已了解基础 — 必要背景/链接仍要
2. 不要堆砌术语 — 首现术语给简短解释
3. **不要泛泛而谈，也不要抠无关紧要的细节** —— 要"抽象具体兼备"：抽象自洽 + 细节到位，缺一不可；切勿掉进无关紧要的实现细节
4. 不要一条路走到底 — 提供对比/取舍，给决策依据
5. 不要忽略实战 — 原理后配可执行的命令（`npm run build` 等）
6. 代码块不要过长 — 5~20 行且有讲解
7. 不要有绝对路径 raw-HTML — 用相对路径（`opencode/`、`./images/…`）
8. 段落不要太长 — 80~200 字，手机阅读友好
